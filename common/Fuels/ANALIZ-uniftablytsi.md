# Аналіз: універсальна Oracle-таблиця для заправок (OKKO, Shell, +майбутні)

> **Статус:** аналітичний документ. Код не пишеться і не переписується — це проєктне
> рішення структури таблиці перед розробкою.
> **Мета:** одна таблиця в Oracle, у яку автоматично (крон-синхронізація) стікаються
> транзакції заправок з різних вендорів (OKKO, Shell, у майбутньому — Укрнафта, WOG та ін.),
> зведені до **єдиної форми** для звітності.

---

## 1. Що ми маємо на вході

Дані приходять із двох вендорських API, які вже нормалізуються в бекенді
(`backend/src/okko/okko.mapper.ts`, `backend/src/shell/shell.mapper.ts`). Тобто «сира»
різнорідність уже частково згладжена — але формати все одно різні, і для БД їх треба звести
ще щільніше.

### 1.1. OKKO — `OkkoTransaction`

REST `gw-online.okko.ua`. Особливості:
- **Валюта завжди UAH.** Гроші в API — у копійках (`/100`), обʼєм — у мілілітрах (`/1000`);
  бекенд це вже конвертує.
- **Ціна одиниці — похідна** (`сума / обʼєм`), її не беруть із відповіді напряму.
- **Знижка є явно:** `amount_discount` (сума знижки), `price_discount` (ціна зі знижкою).
- **Немає ПДВ окремо** — сума `amnt_trans` уже валова (gross), нетто/ПДВ не розділені.
- **Водій — опосередковано:** у транзакції немає ПІБ водія; є `card_num`, а власник картки
  (`card_owner_*`) живе в довіднику карток, не в транзакції.
- **Немає держ. номера ТЗ** у транзакції.
- **Тип операції** — числові коди (774/775/783/787/737) → опис + прапорець `is_return`.

Ключові поля: `trans_id`, `trans_date`, `card_num`, `azs_name`, `addr_name`, `product_id`,
`product_desc`, `price`, `price_discount`, `volume`, `amnt_trans`, `amount_discount`,
`trans_type` + `trans_type_desc`, `reversal`, `is_return`.

### 1.2. Shell — `ShellTransaction`

POST `api-test.shell.com` (тестове середовище). Особливості:
- **Мультивалютність.** Суми — у валюті інвойсу (`EUR` тощо). Бекенд тримає **дві копії**:
  оригінал (`Source*`) і сконвертоване в UAH за курсом (`ExchangeRate`), щоб зводити з OKKO.
- **Нетто/валова окремо:** є `NetAmount` і `GrossAmount` → **ПДВ обчислюваний** (gross − net).
- **Немає явної знижки** окремим полем (є лише `UnitPrice`).
- **Водій І номер ТЗ присутні:** `DriverName`, `VehicleRegistration` — прямо в транзакції.
- **Не лише пальне:** Shell повертає й комісії, мийки, толлінг, коригування — тому є
  `FuelProduct`, `IsFee`, `ProductGroupId`/`ProductGroupName`.
- **Дати компактні** `YYYYMMDD` → бекенд нормалізує в ISO.
- Ідентифікатори: `TransactionId` + `SalesItemId` (рядок продажу).

Ключові поля: `TransactionId`, `SalesItemId`, `TransactionDate`, `PostingDate`, `CardPAN`,
`DriverName`, `VehicleRegistration`, `SiteCode`, `SiteName`, `SiteCountry`, `ProductCode`,
`ProductName`, `Quantity`, `UnitPrice`, `NetAmount`, `GrossAmount`, `CurrencyCode`,
`Source*`, `ExchangeRate`, `Type`, `ProductGroupId/Name`, `FuelProduct`, `IsFee`, `IsReturn`,
`TransactionTypeCode`, `TransactionTypeDescription`.

## 2. Порівняння «поле-до-поля» (карта уніфікації)

| Уніфіковане поняття        | OKKO                                   | Shell                                       | Коментар / пастка |
|----------------------------|----------------------------------------|---------------------------------------------|-------------------|
| Вендор / бренд             | `'OKKO'` (константа)                    | `'SHELL'` (константа)                        | у джерелі відсутнє — проставляється при завантаженні |
| Ід. транзакції (вендорський)| `trans_id`                            | `TransactionId` (+ `SalesItemId`)           | у Shell один інвойс має кілька рядків → природний ключ **пара** `TransactionId+SalesItemId` |
| Дата/час операції          | `trans_date` (ISO)                     | `TransactionDate` (ISO після мапінгу)       | Shell ще має `PostingDate` (дата рознесення) |
| № картки                   | `card_num`                             | `CardPAN`                                    | у OKKO повний, у Shell — PAN (маскований) |
| Водій (ПІБ)                | ❌ (лише через довідник карток)         | `DriverName`                                 | OKKO не дає в транзакції → лишиться NULL, тягнеться з картки |
| Держ. номер ТЗ             | ❌                                      | `VehicleRegistration`                        | OKKO не дає → NULL, привʼязка до `TZ` за карткою |
| Код АЗС / станції          | `azs_name`/`ext_azs`                   | `SiteCode`                                   | OKKO ідентифікує назвою/зовн. кодом, Shell — числовим кодом |
| Назва АЗС                  | `azs_name`                             | `SiteName`                                   | |

| Ціна зі знижкою            | `price_discount`                       | ❌                                           | Shell знижку окремо не віддає |

| Сума нетто (без ПДВ)       | ❌                                      | `NetAmount` / `SourceNetAmount`              | OKKO не розділяє; ПДВ Shell = gross − net |
| Сума знижки                | `amount_discount`                      | ❌                                           | |
| % знижки                   | ❌ (обчислюється)                       | ❌                                           | похідне: `сума_знижки / сума_повна` |
| Валюта                     | `'UAH'`                                | `CurrencyCode` (EUR/…)                       | ключова різниця — див. §3.1 |
| Курс до UAH                | `1`                                    | `ExchangeRate`                               | OKKO завжди 1 |
| Сума в UAH (нормалізована) | = `amnt_trans`                         | `GrossAmount` (уже UAH)                      | базова валюта звіту — гривня |
| Код типу операції          | `trans_type` (774/775/…)               | `TransactionTypeCode` (`SHELL_G<id>`/`SHELL_FEE`) | різні кодування → зберігаємо як текст |
| Опис типу операції         | `trans_type_desc`                      | `TransactionTypeDescription`                 | |
| Повернення / сторно        | `is_return` / `reversal`               | `IsReturn`                                   | обидва мають прапорець |
| Це пальне?                 | (майже завжди так)                     | `FuelProduct`                                | Shell має і непаливні операції |
| Це збір/комісія?           | ❌                                      | `IsFee`                                       | OKKO таких, як правило, немає |

## 3. Пастки, які визначають структуру таблиці

### 3.1. Валюта і курс — **найважливіше**
OKKO — завжди UAH. Shell — інвойс у EUR (чи іншій), з окремим курсом. Тому в таблиці потрібні
**три «грошові виміри»**, як це вже робить бекенд Shell:
1. `валюта` + `курс` — оригінальна валюта вендора та курс до UAH;
2. `сума_ориг` — сума у валюті інвойсу (для звірки з первинними документами вендора);
3. `сума_uah` — сума, конвертована в гривню (для зведеної звітності поряд з OKKO).

Зберігати **лише UAH — помилка**: втратимо звірку з інвойсами Shell. Зберігати лише
оригінал — не зведемо звіт. Тримаємо обидва.

### 3.2. Нетто / ПДВ
Shell дає `NetAmount`; OKKO — ні. Тому колонки `сума_нетто` та `пдв` мусять допускати NULL
(для OKKO вони порожні або обчислюються за ставкою окремо). Не «підганяти» OKKO під нетто
штучно.

### 3.3. Знижка
OKKO дає `amount_discount`/`price_discount`; Shell — ні. Колонки знижки — nullable. Це
пояснює, чому в `CCINVOICED` знижка (`sumazn`, `cinazn`, `przn`) відділена від повної суми
(`sumafull`, `cinafull`) та кінцевої (`suma`, `cina`).

### 3.4. Ідентичність запису / дедуплікація
Крон качатиме перекривні діапазони (self-heal), тому **обовʼязковий природний ключ** проти
дублів:
- OKKO: `trans_id`.
- Shell: пара `TransactionId` + `SalesItemId` (один інвойс = багато рядків).

Рішення: колонка `natural_key` = `вендор` + вендорський ідентифікатор(и), з **UNIQUE**-обмеженням.
Завантаження — `MERGE` (upsert) за цим ключем, не сліпий `INSERT`. Це прямий аналог
`cctrans` у `CCINVOICED` («транзакція по інвойсу: дата,час та кред. картка»), але надійніший,
бо базується на ID вендора.

### 3.5. Повернення/сторно і не-пальне
Треба зберегти прапорці `is_return` та `is_fee`/`is_fuel`, щоб звіти могли: (а) віднімати
повернення, (б) відділяти пальне від комісій/мийок. Інакше сума пального «попливе».

### 3.6. Різні одиниці/типи пального
`product_id`/`ProductCode` — з вендорських довідників, несумісні між собою. Потрібен **власний
довідник типів пального** (наш `code_pal`), у який мапляться вендорські коди. У таблиці
зберігаємо і сирий вендорський код/назву, і (nullable) наш нормалізований `code_pal`.

### 3.7. Привʼязка до внутрішніх сутностей (ТЗ, водій, картка)
Звіти в системі оперують `kod_tz` (авто), `kod_os` (працівник), `kod_cc` (картка) —
див. `CCINVOICED`. Вендор дає лише **зовнішні** ідентифікатори (№ картки, іноді держ. номер).
Тому в таблиці корисно мати **обидва шари**:
- «сирі» вендорські поля (№ картки, ПІБ водія, держ. номер) — заповнюються при завантаженні;
- «розвʼязані» FK (`kod_cc`, `kod_tz`, `kod_os`) — заповнюються **окремим кроком зіставлення**
  (по № картки → `CC`, і далі), можуть лишатися NULL, поки не зіставлено.

Не варто вимагати FK при вставці — вендорський запис має приземлитися навіть без привʼязки,
а звʼязування робити фоновою процедурою.

## 4. Спільне ядро полів (те, що є/виводиться у всіх вендорів)

Це той універсальний набір, який тримається окремо від вендор-специфіки:

- **Джерело:** вендор/бренд, вендорський ID(и), природний ключ.
- **Час:** дата/час операції (+ дата рознесення, де є).
- **Ідентифікація суб'єкта:** № картки, (ПІБ водія), (держ. номер ТЗ).
- **Місце:** код станції, назва, адреса/країна.
- **Товар:** вендорський код + назва продукту, наш `code_pal`, прапорець «пальне».
- **Кількість:** літри.
- **Гроші:** валюта, курс, ціна за од. (ориг/UAH), сума валова (ориг/UAH), сума нетто (де є),
  ПДВ (де є), знижка (сума/ціна/%, де є).
- **Класифікація операції:** код типу, опис, `is_return`, `is_fee`.
- **Службові:** сирий JSON відповіді (аудит), дата/час синхронізації, прапорці
  `isignore`/`nosyn` (як у CCINVOICED), звʼязок з майбутнім інвойсом/звітом.

## 6. Як це співіснує з наявною `CCINVOICED`

`AGTDAT.CCINVOICED` («Записи інвойсу») — це вже **уніфікована** таблиця рядків інвойсу з
розділеними ціною/знижкою/повною (`cina`/`cinazn`/`cinafull`, `suma`/`sumazn`/`sumafull`),
привʼязками (`kod_tz`, `kod_os`, `kod_cc`, `kod_kraina`, `kod_valut`), брендом (`brend`),
станцією (`station`) і полем `cctrans` (звірка з транзакцією).

Рекомендована роль нової таблиці — **шар «сирого прийому» (ingest / staging)** перед інвойсами:

```
Вендор API → (крон-синхронізація) → CCFUELTX  → (зіставлення + формування) → CCINVOICED
   OKKO/Shell/…        upsert          сирі,          привʼязка kod_*,          рядки інвойсу
                     дедупл. за        зведені        інвойсування
                     natural_key       транзакції
```

- `CCFUELTX` тримає **кожну транзакцію як факт** із джерела, з дедуплікацією й аудитом.
- `CCINVOICED` лишається бізнес-рівнем (інвойси, звіти, фін. привʼязки).
- Поля-двійники (`cina/cinazn/cinafull`, `suma/sumazn/sumafull`, `brend`, `station`,
  `code_pal`, `kod_*`, `przn`, `nosyn`, `isignore`) навмисно повторюють конвенцію
  `CCINVOICED`, щоб перехід «транзакція → рядок інвойсу» був прямим.

> Альтернатива: якщо політично вирішать **не** множити таблиці — можна розширити `CCINVOICED`
> кількома колонками (`vendor`, `vendor_tx_id`, `natural_key`, `valuta`, `kurs`,
> `suma_uah`, `is_return`, `is_fee`, `raw_json`) і качати прямо в неї. Мінус: змішуються
> «сирий прийом» і «бізнес-інвойс», важче чистити дублі й переливати. **Рекомендація —
> окрема `CCFUELTX`.**

## 7. Розширюваність під майбутніх вендорів (Укрнафта, WOG, …)

Схема свідомо **вендор-агностична**:
1. **Новий вендор = новий рядок у `vendor`,** без зміни DDL. Уся специфіка живе в мапері
   на боці бекенду (як зараз `okko.mapper.ts` / `shell.mapper.ts`), який зводить сирий
   формат вендора до цих колонок.
2. **Валюта/курс/нетто/знижка вже передбачені як nullable** — покриють будь-яку комбінацію:
   вендор у UAH без нетто (як OKKO), вендор у валюті з нетто (як Shell), вендор зі знижкою
   тощо.
3. **`raw_json`** зберігає повну сиру відповідь — якщо в майбутнього вендора зʼявиться поле,
   якого ми не передбачили, воно не втрачається і його можна дістати без ре-інтеграції.
4. **Довідник типів пального** (`code_pal`) — єдина точка, куди додається мапінг кодів нового
   вендора; звіти лишаються стабільними.
5. **`natural_key` з префіксом вендора** гарантує, що ID різних вендорів не колізують.

Мінімальний чекліст підключення нового вендора:
- [ ] написати мапер вендор→уніфікована форма (аналог наявних);
- [ ] додати мапінг його кодів пального в довідник `code_pal`;
- [ ] визначити його природний ключ (що = унікальний рядок транзакції);
- [ ] додати гілку в крон-синхронізацію (upsert за `natural_key`).

## 8. Відкриті питання (потрібне рішення бізнесу/ДБА)

1. **Окрема `CCFUELTX` чи розширення `CCINVOICED`?** (рекомендація — окрема; §6).
2. **Гранулярність Shell:** зберігати кожен `SalesItemId` окремим рядком (рекомендовано) чи
   згортати інвойс у один запис? Впливає на природний ключ.
3. **ПДВ для OKKO:** лишати NULL чи обчислювати за ставкою 20%? (OKKO нетто не віддає).
4. **Джерело курсу для Shell:** курс вендора з інвойсу (`ExchangeRate`) чи курс НБУ на дату?
   Впливає на `suma_uah` і звірку.
5. **Політика перезавантаження:** ширина перекривного вікна крона (self-heal) і чи
   оновлювати вже завантажені рядки при повторному MERGE (напр., якщо вендор пост-фактум
   змінив статус/суму).
6. **Продове середовище Shell:** зараз інтеграція на `api-test.shell.com` — бойові облікові
   дані ще не надані; структура від цього не залежить, але обсяг/поля треба перевірити на
   проді.
