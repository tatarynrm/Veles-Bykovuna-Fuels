## 2. Коротко: що важливо знати до проєктування

1. **Первинний ключ — поле `ID` (30 символів), а не `REF + REFN`.** Банк радить `REF+REFN`, але на реальних даних він **не унікальний**: 253 пари рядків із 56 910 (внутрішні перекази між нашими рахунками дають два рядки — дебет і кредит — з однаковими `REF+REFN`). `ID` унікальний без винятків. Деталі — розділ 7.
2. **Сума завжди додатна, напрямок — у `TRANTYPE`** (`D` — списання, `C` — надходження). Мінусів і нулів немає.
3. **Усі суми й дати приходять рядками**: `"1234.56"`, `"06.11.2026"`, `"06.11.2026 09:33:00"`. Формат дат — `ДД.ММ.РРРР`, не ISO. Часового поясу немає (київський час).
4. **62 % рядків (35 270) — операції по корпоративних картках.** Для них корисна інформація (картка, момент операції, категорія, мерчант) **живе всередині тексту `OSND`**, а контрагент — технічний рахунок банку («USD валютна позиція…»). Розділ 8.
5. **Одну й ту саму транзакцію API може віддати двічі** (на межі сторінок виявлено 1 такий випадок із 571 сторінки). Записувати слід через `MERGE`/upsert за `ID`.
6. **Три різні стани «значення немає»**: ключ відсутній, `null`, порожній рядок `""`. У БД усе це — `NULL`.
7. **Поле `TECHNICAL_TRANSACTION_ID` завжди `null`**, `FL_REAL` і `PR_PR` завжди `r` — на практиці це константи.
8. **В одній виписці — кілька власних рахунків** (UAH, EUR, цільовий, соцстрах, зарплатний) **і навіть рахунок самого банку** (кредитний, 14 рядків) — отже `AUT_MY_*` не є константою компанії.
9. **Обсяг невеликий**: ≈ 2 600 рядків на місяць (1 943 – 3 163), ≈ 30 тис. на рік, ≈ 1,1 КБ сирого JSON на рядок (весь історичний масив — 60 МБ).
10. **У тексті є персональні дані фізичних осіб** (ПІБ, ІПН у призначенні платежів, ІПН ФОП як код контрагента) — таблицю слід вважати конфіденційною.

## 3. Як працює API

### 3.1. Загальне

| | |
|---|---|
| Базовий URL | `https://acp.privatbank.ua` |
| Метод | `GET` (для виписок) |
| Автентифікація | заголовок `token: <токен із налаштувань «Інтеграція (Автоклієнт)»>` |
| Обов'язкові заголовки | `User-Agent`, `token`, `Content-Type` |
| Кодування | банк підтримує `utf-8` і `cp1251`. **Якщо charset у `Content-Type` не вказано — відповідь у `cp1251`.** Ми шлемо `Content-Type: application/json;charset=utf-8` і отримуємо коректний UTF-8 🔵 |
| Частота запитів | рекомендовано **не частіше 1 запиту/с** 🟢 |
| TLS | 1.0 та 1.1 не підтримуються |
| Режим «група ПП» | тільки якщо «Автоклієнт» створено для групи; тоді в усі запити треба додавати `id=<клієнт групи>`, інакше `400` 🟢 (у нас не використовується) |

### 3.2. Три виписки

| Ендпоінт | Що повертає | Параметри | `limit` |
|---|---|---|---|
| `GET /api/statements/transactions` | транзакції **за інтервал дат** | `startDate` (обов'язково), `endDate`, `acc`, `followId`, `limit` | за замовч. 20, макс. **500** (радять ≤ 100) |
| `GET /api/statements/transactions/interim` | **проміжні** дані — від `lastday` до `today` (поточний операційний день) | `acc`, `followId`, `limit` | макс. **100** |
| `GET /api/statements/transactions/final` | дані за **останній підсумковий день** | `acc`, `followId`, `limit` | макс. 500 (радять ≤ 100) |
| `GET /api/statements/settings` | серверні дати й фаза роботи | — | — |

- Формат дат у запиті: **`ДД-ММ-РРРР`** (з дефісами!), у відповіді — `ДД.ММ.РРРР` (з крапками).
- Обидві межі періоду **включні** (перевірено: рядки `01.01.2025` і `06.11.2026` у вибірці є).
- Без `acc` — дані по **всіх активних рахунках**.
- Якщо `phase` у `settings` не `WRK` — запити можуть падати з помилками 🟢. Якщо `work_balance = Y` — іде регламент, запитів не робити 🟢.

### 3.3. Пагінація (курсор)

Відповідь містить `exist_next_page` і `next_page_id`. Поки `exist_next_page = true`, `next_page_id` підставляємо в наступний запит як `followId`.

Спостереження 🔵:
- `next_page_id` **дорівнює `ID` останнього рядка сторінки** (перевірено на `interim` і `final`).
- Рядки йдуть **за зростанням часу** (`DATE_TIME_DAT_OD_TIM_P`).
- Через курсор **на межі сторінок рядок може повторитися** — тому upsert за `ID`.

### 3.4. Чи однакові рядки в різних виписках

Перевірено порівнянням: перші 100 рядків `interim` і 100 рядків `final` **повністю збігаються (усі поля) з тими самими `ID` у виписці за період** 🔵. Тобто один і той самий `ID` — та сама транзакція в усіх трьох виписках.

У `interim` ми **жодного разу не бачили `PR_PR = p`** (проводиться): усі рядки вже `r`. Чи можуть рядки змінюватися після потрапляння у виписку — **не підтверджено** (див. розділ 13), тому синхронізацію варто робити з перечитуванням «хвоста» за кілька днів.

### 3.5. `settings` (зразок реальної відповіді)

| Поле | Значення (приклад) | Опис (🟢 банк) |
|---|---|---|
| `phase` | `WRK` | фаза роботи; не `WRK` — запити можуть повертати помилки |
| `dates_without_oper_day` | `["01.01.2018 00:00:00", …]` | дні без операційного дня |
| `today` | `06.11.2026 00:00:00` | поточний операційний день (для проміжної виписки) |
| `lastday` | `05.11.2026 00:00:00` | попередній операційний день (для проміжної) |
| `work_balance` | `N` | `N` — запити можна, `Y` — регламент, запитів не робити |
| `server_date_time` | `06.11.2026 11:47:25` | час сервера |
| `date_final_statement` | `13.04.2026 00:00:00` | «дата, включно з якої є підсумкова виписка» — **у нас вона відстає від реальності**: `final` віддав рядки за 04.11.2026 🔵 |

## 4. Конверт відповіді

```json
{
  "status": "SUCCESS",
  "type": "transactions",
  "exist_next_page": true,
  "next_page_id": "XXXXXXXXXXXXXX0000000000000000X",
  "transactions": [ { …транзакція… }, … ]
}
```

| Поле | Тип | Опис |
|---|---|---|
| `status` | string | `SUCCESS`. **Помилку банк може повернути з HTTP 200 і `status: "ERROR"`** — перевіряти треба обидва 🔵 (так робить і наш адаптер) |
| `type` | string | `transactions` (для балансів — `balances`, для налаштувань — `settings`) |
| `exist_next_page` | boolean | чи є наступна сторінка |
| `next_page_id` | string | курсор для `followId` (= `ID` останнього рядка) 🔵 |
| `transactions` | array | рядки транзакцій |

## 5. Поля транзакції — повна розшифровка

Всього **41 ключ** у живих даних + ще 2, які є в описі банку, але **жодного разу не з'являлися** (`PAYER_ULTMT_DOCUMENT`, `PAYER_ULTMT_COUNTRY_CODE`).
Усі значення в JSON — **рядки** (єдиний виняток: `null`). Тип «str» не повторюю.

Колонка «Oracle» — **рекомендація**, не вимога.

### 5.3. Гроші

| Поле | Формат | Заповн. | Опис | Дж. | Oracle |
|---|---|---|---|---|---|

## 7. Ключі, унікальність, дублікати

### 7.1. Структура `ID`

```
ID = REF(14) + REFN(1) + DDMMYYYY(8) + HHMM00(6) + TRANTYPE(1)   = 30 символів

  DNHAAAAAAAAAAA  1  14102026  030500  D
  └── REF ──────┘  │  └ DAT_OD ┘└ час ┘ └ TRANTYPE
                 REFN
```

Перевірено на **всіх 56 910 рядках без винятків** 🔵: початок `ID` = `REF`+`REFN`; наступні 8 цифр = `DAT_OD` у вигляді `ДДММРРРР`; наступні 6 = `ГГХХ` з `TIM_P` + `00`; останній символ = `TRANTYPE`.
Це **ознака, що `ID` вбудовує напрямок (`D`/`C`)**, — через що обидві ноги внутрішнього переказу мають різні `ID`.

### 7.2. Що унікальне, а що ні

| Кандидат у ключ | Унікальний? | Коментар |
|---|---|---|
| **`ID`** | ✅ **так** (56 910 з 56 910) | **рекомендований PK** |
| `REF + REFN` | ❌ **ні** — 253 колізії по 2 рядки | це те, що радить банк; **не підходить** (див. 7.4) |
| `REF + REFN + AUT_MY_ACC + TRANTYPE` | ✅ так | природний складений ключ, якщо `ID` не хочеться брати як PK |
| `REF` | ❌ ні | під одним `REF` — від 1 до 2 рядків (4 406 пар) |
| `NUM_DOC` | ❌ ні | |
| `UETR`, `DLR` | ❌ ні | діляться між рядками одного платежу |

### 7.3. Дублікати в самих відповідях

- На межі сторінок API може повернути **той самий рядок двічі**: 1 випадок на 571 сторінку (ідентичні рядки з однаковим `ID`) 🔵. → завантаження через `MERGE … ON (ID)`.
- Той самий `ID` у виписках `transactions`, `interim` і `final` — **той самий рядок** (відповідність за всіма полями) 🔵.

### 7.4. Внутрішні перекази: два рядки з одним `REF+REFN`

Коли гроші переходять між **нашими** рахунками (UAH↔UAH, EUR↔EUR), банк віддає **два рядки** з однаковими `REF`, `REFN`, `SUM`, датою й часом:

| | рахунок | `TRANTYPE` | `ID` (хвіст) |
|---|---|---|---|
| нога 1 | джерело (наш рахунок А) | `D` | `…0300D` |
| нога 2 | приймач (наш рахунок Б) | `C` | `…0300C` |

Ознаки такого переказу 🔵: `AUT_CNTR_CRF = AUT_MY_CRF` і `AUT_CNTR_ACC` — один із наших рахунків. Таких пар — 253 (506 рядків із 56 910). Для **аналітики** (обороти, витрати) обидві ноги слід **виключати або згортати**, інакше рух коштів задвоюється.

## 8. Розбір `OSND` (призначення платежу)

`OSND` — не просто примітка, у ньому лежить значна частина корисної інформації.

### 8.1. Операції по корпоративних картках — **35 270 рядків (62 %)**

Ознака: `OSND` починається з маски картки. Структура (збігається у 99,7 % рядків):

```
<NNNN **** **** NNNN> <ДД.ММ.РРРР ГГ:ХХ:СС> <Категорія>: <опис / мерчант>
 └ маска картки ┘      └ момент операції ┘     └ категорія ┘  └ вільний текст ┘
```

Приклад (вигаданий): `4246 **** **** 0000 12.10.2026 18:41:07 Авто: EXAMPLE FUEL, CITY`

Властивості 🔵:
- маска завжди у форматі `NNNN **** **** NNNN` (перші 4 і останні 4 цифри); **212 різних масок**; перші цифри (BIN): `4246` (21 760), `5169` (12 707), `5329` (705), `4149` (68), `5168` (27);
- **момент операції по картці ≠ `DAT_OD`**: `DAT_OD` пізніший на 0–10 днів (найчастіше 2 дні) — розрахунок через платіжну систему; для звітів «коли заправились» треба брати час **з тексту `OSND`**;
- `CCY` = `UAH` завжди, `TRANTYPE` = `D` (лише 4 рядки `C` — з текстом «Зарахування: …», це надходження на картку), `DOC_TYP` = `m` (є 98 з `p` — виплати фізособам на картки);
- **контрагент — не продавець**, а технічні рахунки банку: «USD валютна позиція (Compass, ISS1)» — 21 260, «EUR валютна позиція (Compass, ISS1)» — 6 530, «Розрахунки за картками (С+, ACQ2)» — 5 370, «Розрахунок ПО Mastercard(COMPASS+-Емісія)» — 992, «Розрахунок VISA (COMPASS+-Емісія)» — 690 …; 43 різні рахунки;
- сума `SUM` — **у гривнях за курсом розрахунку**, оригінальної суми й валюти покупки в окремих полях **немає**.

### 8.3. Податкові платежі: структурований префікс

Для податків `OSND` починається з `*;`, далі — поля, розділені `;` (так вимагає формат НБУ/ДПС):

```
*;<код виду сплати>;<код бюджетної класифікації>;<код платника>;<…>;<вільний текст>
```

Приклад (вигаданий): `*;101;11010100;12345678;;; ПДФО з заробітної плати за жовтень 2026`

Тобто **КБК і код виду сплати треба дістати саме з `OSND`**, а не з `STRUCT_TYPE` (він порожній).
Окремий різновид — штрафи: `*;ЕНА;…;* за ПІБ по постанові ЕНА №… від …` (містить **ПІБ фізособи**).

### 8.4. Виплати фізичним особам

`OSND` може містити **ПІБ та ІПН фізичних осіб** (наприклад, перерахування на картку працівника: `NNNN **** **** NNNN ІПН NNNNNNNNNN <ПІБ> ос. рах NNNN…`). Це **персональні дані** — доступ до таблиці обмежити, логувати.

## 10. Розбіжності між документацією банку і реальними даними

Це місця, де офіційний опис вводить в оману. Усі перевірені на живих даних.

| # | Що пише банк | Що насправді | Наслідок для БД |
|---|---|---|---|
| 1 | «Для ідентифікації унікальності платіжних інструкцій використовуйте `REF+REFN`» | `REF+REFN` має **253 колізії** (внутрішні перекази) | PK — `ID`, а не `REF+REFN` |
| 2 | `ID` — число (`"557091731"`) | `ID` — **30-символьний складений рядок** | `VARCHAR2(30)`, не `NUMBER` |
| 3 | `TECHNICAL_TRANSACTION_ID` = `"557091731_online"` | **завжди `null`** | колонка не потрібна |
| 4 | `REFN` — «№ з/п всередині проведення» (число) | символ: `1`, `P`, `Y`, `A` | `VARCHAR2`, не `NUMBER` |
| 5 | `AUT_MY_*` — «ЄДРПОУ / рахунок / назва **одержувача**» | наш рахунок у виписці, незалежно від напрямку | не плутати з «одержувачем» |
| 6 | `AUT_MY_CRF` — одна компанія | може бути **інший власник** (рахунок самого банку, 14 рядків) | не вважати константою |
| 7 | `STRUCT_TYPE` — КБК (`22080000`) | завжди `""`; КБК лежить в `OSND` | розбирати `OSND` |
| 8 | `Content-Type: application/json;charset=cp1251` | працює й `utf-8`; **без charset — cp1251** | завжди вказувати `charset=utf-8` |
| 9 | `date_final_statement` — «дата, включно з якої є підсумкова виписка» | `13.04.2026`, тоді як `final` віддає рядки за `04.11.2026` | на це поле не спиратись |
| 10 | `PR_PR`: `p`/`t`/`r`/`n` | у `interim` і `period` — лише `r` | стан не змінюється на наших даних, але колонку тримати |
| 11 | `AUT_MY_MFO_CITY` — «Київ» (у прикладі) | `ДНІПРО` (великими) | регістр непостійний |
| 12 | `limit` за замовч. 20 | наш адаптер бере 100; макс. 500 (для `interim` — 100) | для великого завантаження доцільно 500 *(не перевірялось)* |

### 11.1. Основна таблиця (факт)

Одна таблиця «транзакції виписки». Рекомендації:

| Рішення | Чому |
|---|---|
| **PK = `ID` `VARCHAR2(30)`** | єдиний гарантовано унікальний ключ (розділ 7) |

## 12. Зауваження до нашого бекенду

Код у `backend/src/privat/` (мапер `privat.mapper.ts`, адаптер `privat-api.service.ts`) був написаний за офіційним описом, тому повторює пункт 1 розділу 10:

- `id` у нашій нормалізованій транзакції = `REF + REFN` (`mapTransaction`).
- `dedupeTransactions()` відкидає рядки з однаковим `id`.

**Наслідок на реальних даних:** кожна друга нога внутрішнього переказу **відкидається як «дубль»** — за весь період це 253 рядки з 56 910 (≈ 0,4 %), і підсумки по рахунках у `summarize()` стають незбалансованими (одна нога є, другої немає).
**Виправлення просте:** брати `id` = поле `ID` банку (а при його відсутності — складений ключ `REF+REFN+AUT_MY_ACC+TRANTYPE`) і лишати дедуплікацію лише по ньому. Це не входило в це завдання (лише документація), тому **код не змінювався**.

Ще дрібниці, які варто врахувати при зберіганні:
- `toIsoDateTime()` для `DATE_TIME_DAT_OD_TIM_P` дає `YYYY-MM-DDTHH:MM:SS` без зони — це правильно, пояс київський.
- `real_flag`, `status` вже зберігаються — добре, бо в API документовані значення, яких ми ще не бачили.

## 13. Відкриті питання до банку

Те, чого з опису й даних зрозуміти не вдалося — варто уточнити в підтримці Приват24 для бізнесу (`api.privatbank.ua`, «Автоклієнт»):

1. **`DOC_TYP`** — повна легенда кодів (`m`, `p`, `r`, інші).
2. **`FL_REAL`** — що означають `r` та `i`.
3. **`ULTMT`** — розшифровка `N`, `D`, `A` (і чи є інші).
4. **`REFN`** — повна легенда (`1`, `P`, `Y`, `A`); чому не число, як в описі.
5. **`DLR`** — формат; чому для частини рядків `null`, для частини `""`.
6. **`ID`** — чи гарантується стабільність формату (30 символів) і чи гарантується, що він не змінюється при переході рядка з `interim` → `final`.
7. **Чи можуть уже віддані рядки змінюватися** (стани `p` → `r`/`t`/`n`; сторно): ми бачили лише `r`.
8. **`SUM_E` для валютних рахунків** — яким курсом і на яку дату рахується гривневий еквівалент.
9. **`date_final_statement`** у `settings` відстає на сім місяців від реальних підсумкових даних — це помилка чи окреме значення?
10. Чи можна для карткових операцій отримувати **оригінальну суму й валюту** покупки та ідентифікатор терміналу/мерчанта окремими полями (зараз — лише текст у `OSND`).
